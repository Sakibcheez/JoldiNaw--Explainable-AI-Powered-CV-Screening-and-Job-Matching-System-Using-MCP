# Security and privacy

All record endpoints validate bearer tokens and stored organization membership. REST writes require recruiter/admin role and write scope. Read access to recruiting records is limited to admin/recruiter/viewer memberships; the `user` role is restricted to identity lookup and is denied record reads, mutations, and MCP tools. MCP requires mcp:read plus a recruiting-workspace role on every call; allowed host/origin transport validation remains active. Production requires PostgreSQL/RQ and configured OIDC RS256 signature, issuer, audience, expiry and subject verification. Provision memberships explicitly using `python -m scripts.provision_identity`; no self-provisioning or production demo bypass exists.

Upload controls: PDF/DOCX signature allowlist, 10 MB limit, 50-page PDF limit, 100k extracted-character limit, bounded DOCX ZIP expansion, encrypted/macro DOCX rejection, random storage names and no public file-serving route. RQ imposes a task timeout; production worker resource limits reduce exposure. Antivirus/content-disarm is not implemented; add isolated malware scanning before processing real applicant files. Image-only PDFs fail with an OCR message; OCR is not included.

CV/job/tool text is never executed or used as authentication policy. UI escapes text through React. OIDC tokens stay in sessionStorage; the frontend uses Authorization Code with PKCE (`S256`) and validates state before token exchange. Protect the origin, enforce TLS, register only exact callback URLs, and restrict token-endpoint CORS to trusted frontends. Signup is handled by the configured identity provider; requested roles are checked against provisioned memberships and do not grant permissions. Review/notes are protected data. No email/name inference or automatic rejection is performed.

Deletion removes the private original, passages, derived result/review rows and batch input references. Minimal audit events retain IDs/action/actor without CV text. Backups can retain deleted data until their own expiry: establish and disclose retention. Atomic deletion across filesystem and database is not guaranteed; an orphan-file reconciliation job is needed for crash recovery.

Defense gaps before real-world rollout: independent penetration/privacy review, antivirus isolation, malware fixtures, distributed rate limits (API limiter is per-process), durable transactional outbox/recovery for queue handoff, stale-worker reconciliation, PostgreSQL RLS, access-token UI integration, automatic retention enforcement and measured fairness audits. API membership checks are mandatory; RLS is not currently enabled. Production authentication settings must be verified against your own identity provider.
